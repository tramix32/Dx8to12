# DX8→DX12 coverage roadmap

Started 2026-08-23 at: `IDirect3DDevice8` has 100 methods; 50 have real implementations, 50 are stubs (`NOT_IMPLEMENTED()` → abort at runtime). `IDirect3DSurface8` only implements `GetDesc`. Prioritized by "how likely is this to crash a real game" vs. implementation cost.

Current state (2026-08-23, end of day): 93/100 `IDirect3DDevice8` methods implemented, 7 stubs remain (listed in Phase 6). `IDirect3DSurface8` fully implements `LockRect`/`UnlockRect`/`QueryInterface`/`GetDevice` on every surface kind (Phase 2). `BaseTexture` (both `IDirect3DTexture8` and `IDirect3DCubeTexture8`) fully implements `QueryInterface`/`GetDevice`/`SetPriority`/`GetPriority`/`GetType`/`SetLOD`/`GetLOD` (see below); only `GetContainer` on surfaces and the private-data trio remain unimplemented/no-op across both.

**Build architecture (verified 2026-08-23): must be x86.** Target games are 32-bit processes; a 64-bit `d3d8.dll` can't be loaded into them regardless of code correctness. This is not a D3D12 limitation — `D3D12.lib`/`d3d12.dll` fully support x86 client processes on x64 Windows via SysWOW64. Confirmed the codebase builds clean as x86 with zero source changes (`VsDevCmd.bat -arch=x86` + same CMake invocation) — output is a genuine `PE32 executable ... Intel i386` DLL. See CLAUDE.md's Build section; always build x86 for anything meant to actually run against a game.

## Phase 1 — Mirror getters (done, 2026-08-23)

State was already tracked on `Device` (`render_state_`, `lights_`, `enabled_lights_`, bound textures/targets, current shader handles, etc.); these `Get*` methods just read it back:

- `GetRenderState` (mirrors `SetRenderState`, uses `RenderState::GetEnumAtIndex`)
- `GetLight`, `GetLightEnable` (mirrors `SetLight`/`LightEnable`, reads `lights_`/`enabled_lights_`)
- `GetMaterial`
- `GetTexture`
- `GetViewport` (mirrors `SetViewport`)
- `GetRenderTarget` (returns the explicitly-bound render target, or the current backbuffer if none was set — mirrors the implicit-backbuffer convention already used by `GetDepthStencilSurface`/`GetBackBuffer`)
- `GetIndices` (mirrors `SetIndices`, reads `bound_index_buffer_`/`bound_base_vertex_`)
- `GetStreamSource` (mirrors `SetStreamSource`; had to add `bound_vertex_stream_strides_` since `SetStreamSource` wasn't storing the stride at all before this)
- `GetVertexShader`, `GetPixelShader`
- `GetVertexShaderConstant` (mirrors `SetVertexShaderConstant`, reads `bound_vs_cregs_`)

Skipped, not implementable as a cheap mirror — their `Set*` counterpart is itself a stub, so there's no state to read back:
- `GetClipPlane` (`SetClipPlane` is unimplemented)
- `GetClipStatus` (`SetClipStatus` is unimplemented)
- `GetPixelShaderConstant` (`SetPixelShaderConstant` is unimplemented)
- `GetCurrentTexturePalette` (palette APIs deliberately return `D3DERR_NOTAVAILABLE`, no palette state exists)

These four need their `Set*` implemented first (small features in their own right), so they've been pushed to Phase 6.

## Real-game feedback (2026-08-23): swap chain creation crash on `D3DFMT_X8R8G8B8`

Second reported crash, deeper into device init than the MSAA one: `ASSERT_HR(Init(presentParams))` in `Device::Create` (`device.cpp`) failing. Root cause: `Device::Init`'s `HR_OR_RETURN(dxgi_factory_->CreateSwapChainForHwnd(...))` was passing `DXGIFromD3DFormat(presentParams.BackBufferFormat)` straight through as the swap chain format. `D3DFMT_X8R8G8B8` — the single most common DX8 backbuffer format, used by nearly every game including both test titles — maps to `DXGI_FORMAT_B8G8R8X8_UNORM`, which `DXGI_SWAP_EFFECT_FLIP_DISCARD` swap chains (what this code uses) reject outright with `DXGI_ERROR_INVALID_CALL`; only the alpha-having variants (`R8G8B8A8_UNORM`, `B8G8R8A8_UNORM`, `R16G16B16A16_FLOAT`) are valid for flip-model. This meant essentially every game requesting the default 32-bit backbuffer format would fail at device creation. `Device::Reset` had the identical bug in its `ResizeBuffers` call.

Fixed with a small `ToFlipModelSwapChainFormat` helper in `device.cpp` that substitutes `DXGI_FORMAT_B8G8R8A8_UNORM` whenever `DXGIFromD3DFormat` would otherwise produce the rejected X8 variant, applied at both call sites (`Init`'s `CreateSwapChainForHwnd` and `Reset`'s `ResizeTarget`/`ResizeBuffers`). Harmless for compatibility: `DXGIToD3DFormat` already maps `B8G8R8A8_UNORM` back to `D3DFMT_A8R8G8B8` for anything that queries the backbuffer format afterward (`GetAdapterDisplayMode`, `GetBackBuffer`'s surface desc, etc.) — the app simply never reads/writes the backbuffer's alpha channel through the X8 format, so gaining one it doesn't ask for is a no-op in practice. This is the standard trick used by essentially every DX8/DX9-on-DX12 or DX8/DX9-on-Vulkan wrapper for exactly this reason.

## Real-game feedback (2026-08-23): `CheckDeviceMultiSampleType`

Reported crash from an actual test run: `IDirect3D8::CheckDeviceMultiSampleType` was a bare `NOT_IMPLEMENTED()` stub, and a real game's adapter-capability probing hit it before device creation even started — this jumps ahead of the phased plan below because it's an empirically confirmed blocker, not a guess.

Fixed in `direct3d8.cpp`: only `D3DMULTISAMPLE_NONE` reports as available (`S_OK`); any actual multisample level returns `D3DERR_NOTAVAILABLE`. This isn't a stopgap — `Device::CreatePSO` always builds PSOs with `SampleDesc.Count = 1`, so there is no real MSAA implementation to honestly report "yes" for. Games probing MSAA levels top-down will fall back to no-AA and continue, instead of believing they got antialiasing they silently didn't. True MSAA support (rendering to a multisampled RT + resolve) would be new work, not covered by this fix — add it here as a later phase if a game turns out to depend on it rather than falling back gracefully.

## Phase 2 — Surface LockRect/UnlockRect (done, 2026-08-23)

Was the highest functional-impact gap: `BaseSurface` only implemented `GetDesc`, so screenshots, render-target readback, and `CreateImageSurface` all aborted.

- `GpuSurface::LockRect/UnlockRect` — on a `D3DPOOL_MANAGED` texture, delegates straight to the owning `GpuTexture`'s per-subresource `LockRect`/`UnlockRect` (already implemented in `texture.cpp`). On `D3DPOOL_DEFAULT` (lockable render targets), goes through the new GPU readback path below.
- `CpuSurface::LockRect/UnlockRect` — reads straight from the footprint/pointer captured at `GetSurfaceLevel` time (`compact_pitch_`/`data_ptr_`), no delegation needed.
- `BackbufferSurface::LockRect` and `GpuSurface::LockRect` (default-pool case) share `BaseSurface::LockGpuReadback`/`UnlockGpuReadback` (`surface.cpp`): create a `D3D12_HEAP_TYPE_READBACK` buffer sized via the new `BaseTexture::GetFootprint` accessor, `CopyTextureRegion` the subresource into it, then call `Device::SubmitAndWait(false)` to flush and block until done (reusing the exact flush-mid-frame path `Device::WaitForFrame` already relies on — no new fence code), then `Map` it. Read-path only; a locked render target is not expected to be written back through `Unlock`.
- `QueryInterface`, `GetDevice` on surfaces — implemented, mirror the equivalent `Device`/`Texture` patterns. `SetPrivateData`/`GetPrivateData`/`FreePrivateData` return `D3DERR_NOTAVAILABLE` (same choice already made for the palette APIs — no private-data storage exists, and returning a clean error is preferable to a fake success). `GetContainer` is still unimplemented (rare, pushed to Phase 6).

## Phase 3 — Standalone surface creation (done, 2026-08-23)

Was blocking shadow maps, extra render targets, offscreen buffers.

All three (`CreateRenderTarget`, `CreateDepthStencilSurface`, `CreateImageSurface`) build directly on `BaseTexture::Create` (single mip level, `D3DUSAGE_RENDERTARGET`/`D3DUSAGE_DEPTHSTENCIL`/`D3DPOOL_SYSTEMMEM` respectively) + `GetSurfaceLevel(0, ppSurface)` — no duplicated resource-desc/footprint logic. Requested `MultiSample != D3DMULTISAMPLE_NONE` logs and silently falls back to single-sample rather than failing, consistent with `CheckDeviceMultiSampleType` (see above) telling callers up front that only no-AA is available.

One easy-to-miss lifetime detail: `BaseTexture::Create` returns an object with an initial refcount of 1 that the app is normally expected to own directly (e.g. `CreateTexture`'s `*ppTexture = BaseTexture::Create(...)`). Here the app never sees the texture, only the surface wrapping it, and `GetSurfaceLevel` internally takes its *own* ref on the texture (`ComWrap` inside the `GpuSurface`/`CpuSurface` constructor) rather than adopting the caller's — so the initial ref has to be explicitly dropped (`ComOwn(texture)` locally, released when it goes out of scope) once the surface has taken its own, or the texture (and its GPU resource / descriptor slots) leaks for the lifetime of the process every single call.

## Real-game feedback (2026-08-23): pixel shader crash on the `_comp` (complement) source modifier

Crash: `ParseSourceParamToken` (`shader_parser.cpp`) FAILed on source modifier value 6 (`D3DSPSM_COMP`, the `1-x` "complement" modifier) for a `ps.1.x` instruction. `ParseShader` is shared by both vertex- and pixel-shader parsing, but the modifier switch only ever handled `D3DSPSM_NONE`/`D3DSPSM_NEG` — every other ps_1_x source modifier (`_bias`, `_bx2`, `_x2`, `_comp`, etc. — common in texture-blend instructions) hit the same `FAIL`.

Fixed by restructuring `ParseSourceParamToken` to build the register+swizzle expression into a local `std::ostringstream` first, then wrap it per-modifier once the modifier is known (previously it streamed straight into the shared `os`, which only allows appending a suffix — enough for `_neg` as `x*-1`, not enough for a modifier like `_comp` that needs to wrap the *whole* expression as `1-x`). Now handles: `NONE`, `NEG` (`-x`), `BIAS` (`x-0.5`), `BIASNEG` (`0.5-x`), `SIGN` (`2x-1`), `SIGNNEG` (`1-2x`), `COMP` (`1-x`), `X2` (`2x`), `X2NEG` (`-2x`). Left unimplemented (still `FAIL`s with a clear message): `DZ`/`DW` (divide-through-by-z/w, used by `texm3x2tex`-style instructions) — these need per-component access to the *same* source register rather than a simple expression wrap, and are rare enough in ps_1_x content to not be worth guessing at blind.

## Phase 4 — State blocks (done, 2026-08-23)

`BeginStateBlock`/`EndStateBlock`/`ApplyStateBlock`/`CaptureStateBlock`/`DeleteStateBlock`/`CreateStateBlock` are implemented via `Device::StateBlock` (`device.h`) — a full snapshot of `RenderState`, `TextureStageState[]`, transforms, material, lights, bound textures, bound vertex/pixel shader handle, and vertex shader constants, stored in `state_blocks_` keyed by a token.

**Documented simplification**: real D3D8 partitions state by `D3DSTATEBLOCKTYPE` (`D3DSBT_ALL`/`D3DSBT_PIXELSTATE`/`D3DSBT_VERTEXSTATE`) and, for a `Begin`/`End`-recorded block, captures only the states actually `Set()` during the recording window — applying the block later only touches those specific states, leaving everything else alone. This implementation always captures/restores the *entire* state listed above regardless of type or what was actually touched. That's harmless for the common case (games tend to save/restore a broad swath of state around a special effect anyway) but can restore more than a game expects if it specifically relies on the precise partitioning or on untouched states surviving an `ApplyStateBlock`. If a game's behavior depends on that, implementing real recording means hooking every `Set*` call to also write into a currently-recording `StateBlock` plus a per-field "was touched" flag — mechanical but touches ~15 call sites, noted here rather than done speculatively.

`ApplyState` stomps `dirty_flags_ |= DIRTY_FLAG_ALL_RESOURCES` unconditionally after restoring, forcing a full re-bind/re-upload before the next draw call rather than tracking exactly what changed — correct but not free; state blocks are not a hot path in typical usage, so this wasn't worth the bookkeeping to avoid.

## Real-game feedback (2026-08-23): `GetTextureStageState` stub, missing `D3DTSS_BORDERCOLOR`

Two more issues found while implementing Phase 4, both pre-existing (not introduced by earlier fixes) and both surfaced by continued real-game testing:

- `Device::GetTextureStageState` was declared `override` in `device.h` (so Phase 1 missed it, reading the header as "already implemented") but its body in `device.cpp` was a bare `NOT_IMPLEMENTED()`. Fixed to mirror `SetTextureStageState` via `TextureStageState::GetAtIndex`. Lesson: the `PURE`-macro coverage check only catches methods that never got a body at all — a method can still be declared `override` and silently stub itself in the `.cpp`. Worth a final sweep for other `NOT_IMPLEMENTED()` calls hiding behind an `override` declaration (see Phase 6).
- Crash: `TextureStageState::GetAtIndex` (`render_state.cpp`) had no case for `D3DTSS_BORDERCOLOR` (value 15) — any game calling `SetTextureStageState`/`GetTextureStageState` with border color (used for `D3DTADDRESS_BORDER` texture wrapping) hit the `FAIL("Unexpected texture stage state")` abort. Added a `border_color` field to `TextureStageState` and wired it into `SamplerDesc`'s `D3D12_SAMPLER_DESC::BorderColor` (`dx_utils.cpp`, via the existing `Dx8::Color` D3DCOLOR→float helper) — previously that field was a `{}`-zeroed `// TODO`, so border-addressed samplers were already silently rendering with black borders instead of the app-requested color even before this crash was reachable.

## Phase 5 — Hardware cursor, and a coverage sweep (done, 2026-08-23)

`SetCursorProperties`/`SetCursorPosition`/`ShowCursor` now wrap `SetCursorPos`/`ShowCursor` (WinAPI). `ShowCursor` tracks its own `cursor_visible_` bool rather than calling Win32 `ShowCursor` unconditionally, since D3D8's version returns the *previous* state and Win32's is a non-idempotent display counter — calling it on every same-value invocation would drift the counter and eventually strand the cursor hidden/shown.

While closing out the easy remaining gaps, also implemented in the same pass: `GetAvailableTextureMem` (fixed 256MB budget — we don't track VRAM usage, and games mostly treat this as a rough heuristic anyway), `GetCreationParameters` (derived from `adapter_index_`/`window_` plus the constants `CreateDevice` already asserts: always `D3DDEVTYPE_HAL` + `D3DCREATE_HARDWARE_VERTEXPROCESSING`), `GetDisplayMode` (delegates to the already-implemented `Direct3D8::GetAdapterDisplayMode`), `ValidateDevice` (always reports 1 pass — we never need multi-pass fallback), `GetCurrentTexturePalette` (now symmetric with `SetCurrentTexturePalette`'s `D3DERR_NOTAVAILABLE`), `SetClipStatus`/`GetClipStatus` (plain struct storage), `SetClipPlane`/`GetClipPlane`, and `SetPixelShaderConstant`/`GetPixelShaderConstant`.

**Bookkeeping-only, documented limitation**: `SetClipPlane`/`GetClipPlane` and `SetPixelShaderConstant`/`GetPixelShaderConstant` store values (so nothing aborts and `Get*` round-trips correctly) but do **not** affect rendering — there is no GPU-side user-clip-plane implementation, and `bound_ps_cregs_` is not wired into the pixel shader's constant buffer. On the pixel-shader-constant front specifically: `programmable_ps.hlsl` currently declares `cbuffer ConstantData : register(b10) { float4 c[NUM_VS_CONST_REGS]; }` — the *same* register slot and size as the vertex shader's constant buffer (`programmable_vs.hlsl`), meaning `c[N]` reads in a ps.1.x shader today actually read the **vertex** shader's constants, not the app's pixel shader constants. There's already an allocated-but-unused `ps_creg_cbuffer_` member (sized for `kNumPsConstRegs`) that looks like an abandoned start at fixing this properly. Wiring it up for real means: uploading `bound_ps_cregs_` into `ps_creg_cbuffer_` (mirroring how `ps_cbuffer_`/`vs_cbuffer_` already get uploaded), adding a new root-signature parameter bound at a distinct register (e.g. `b11`, pixel-visibility only) in `InitRootSignatures`, binding it via `SetGraphicsRootConstantBufferView` at draw time, and changing `programmable_ps.hlsl`'s `ConstantData` to read from that new slot instead of sharing `b10`. Deliberately **not** done here — it touches the root signature/PSO binding layout, which is high-blast-radius and impossible to verify without a real game exercising a ps.1.x shader that actually calls `SetPixelShaderConstant`, so it's left as a scoped, well-understood follow-up rather than guessed at blind.

## Proactive audit (2026-08-23): fixed-function pixel pipeline gaps

Given how well "check every `FAIL()` call against the real D3D8 enum" worked for finding the border-color and shader-modifier crashes, did the same sweep over `ff_pixel_shader.cpp` — the fixed-function texture-stage pixel pipeline, which is the *more* commonly exercised path than programmable ps.1.x shaders for games of this era, so gaps here are higher-probability hits than in the already-covered programmable path.

Found and fixed, all in `ff_pixel_shader.cpp`:
- `D3DTOP_*` (texture stage color/alpha op) coverage was missing `D3DTOP_ADDSIGNED2X`, `D3DTOP_SUBTRACT`, `D3DTOP_ADDSMOOTH`, `D3DTOP_BLENDDIFFUSEALPHA`, `D3DTOP_BLENDTEXTUREALPHAPM` — added all five (straightforward 2-argument HLSL expressions, same shape as the already-handled ops). Left unimplemented: `D3DTOP_LERP`, `D3DTOP_MULTIPLYADD`, `D3DTOP_PREMODULATE`, `D3DTOP_MODULATE*_ADD*`, `D3DTOP_BUMPENVMAP*` — these need a third argument (`D3DTA_*` via `D3DTSS_COLORARG0`/`ALPHAARG0`) that `ApplyOperation`/`GenerateArgValue` don't currently thread through at all; adding one of these means widening that plumbing, not just adding a switch case, so left for when a game actually needs one specifically.
- **Pre-existing bug, not something I introduced**: `D3DTOP_BLENDTEXTUREALPHA`/`D3DTOP_BLENDCURRENTALPHA` used the formula `arg1 + arg2*(1-alpha)` (missing `arg1*alpha`). Per the D3D8 spec all of `BLENDDIFFUSEALPHA`/`BLENDFACTORALPHA`/`BLENDTEXTUREALPHA`/`BLENDCURRENTALPHA` share the same `arg1*alpha + arg2*(1-alpha)` formula, differing only in where `alpha` comes from — the formula that was actually implemented (`arg1 + arg2*(1-alpha)`) belongs to `D3DTOP_BLENDTEXTUREALPHAPM`, the *premultiplied* variant (where `arg1` is deliberately not re-multiplied because the texture already has alpha baked in). Fixed all four non-PM ops to the correct shared formula, and added `BLENDTEXTUREALPHAPM` separately with the formula that was there before.
- `D3DCMP_*` (alpha test comparison function) was missing `D3DCMP_EQUAL`, `D3DCMP_NOTEQUAL`, `D3DCMP_GREATEREQUAL` — `GREATEREQUAL` in particular is a common alpha-cutoff comparison (e.g. foliage/vegetation alpha testing). Added all three.

Not a gap: the auto-texgen mode switch (`D3DTSS_TCI_*`) looked incomplete at first glance (only 3 of 4 modes handled) but the 4th, `D3DTSS_TCI_PASSTHRU`, is value `0` and structurally can't reach that switch (it's only entered when `texcoord_index & ~0xFFFF` is nonzero) — full coverage, no fix needed.

Also not implemented, lower priority: `D3DTA_TEMP` (`GenerateArgValue`'s arg-selector switch) — requires the same triadic-op / `D3DTSS_RESULTARG` plumbing as the ops above, so a standalone fix would be incomplete on its own.

## Proactive audit (2026-08-23): RenderState::GetEnumAtIndex coverage

Same technique applied to `RenderState::GetEnumAtIndex` (`render_state.cpp`) — it backs *both* `SetRenderState` and `GetRenderState`, so a gap there aborts either direction. Diffed the full `D3DRENDERSTATETYPE` enum against the switch's cases and found 26 missing values, added as new `RenderState` fields (`render_state.h`) + switch cases, all bookkeeping-only (documented inline) except where noted:

- **Stencil**: `D3DRS_STENCILFAIL`/`D3DRS_STENCILZFAIL`/`D3DRS_STENCILMASK`/`D3DRS_STENCILWRITEMASK` were missing even though `STENCILENABLE`/`STENCILPASS`/`STENCILFUNC`/`STENCILREF` were already handled — any game using stencil effects (mirrors, shadows, decals) and setting a *complete* stencil state would have hit this. **Important caveat**: adding these fields only stops the abort: `Device::CreatePSO`'s `D3D12_DEPTH_STENCIL_DESC` doesn't set `StencilEnable`/`FrontFace`/`BackFace`/`StencilReadMask`/`StencilWriteMask` at all, so stencil testing does not actually happen on the GPU yet regardless. Wiring it up for real hits the same class of problem as the swap chain fix earlier: `depth_stencil_tex_` is always created as `DXGI_FORMAT_D32_FLOAT`/`DXGI_FORMAT_D16_UNORM` (`Device::Init`/`Device::Reset`), *neither of which has a stencil plane* — enabling `StencilEnable` in the PSO while `DSVFormat` has no stencil channel is invalid and would likely fail `CreateGraphicsPipelineState` outright. A real fix needs the same "substitute a compatible format transparently" trick used for `ToFlipModelSwapChainFormat` (map to `DXGI_FORMAT_D24_UNORM_S8_UINT`/`D32_FLOAT_S8X24_UINT` at the depth-stencil resource creation sites — `Init`, `Reset`, and the Phase-3 `CreateDepthStencilSurface`), plus a `DXGIToD3DFormat` case for the new formats (anything that calls `GetDesc`/`GetSurfaceDesc` on the depth texture would otherwise hit *its* `FAIL("Unimplemented DXGI_FORMAT")` — a new crash surface). Deliberately not done in this pass: real stencil rendering needs those three additional touch points changed together and verified, higher risk than the mechanical coverage fix, and no confirmed game need yet.
- Also added: `D3DRS_CLIPPING`/`D3DRS_CLIPPLANEENABLE`, `D3DRS_LASTPIXEL`, `D3DRS_LINEPATTERN`, `D3DRS_ZVISIBLE` (legacy/deprecated even in D3D8), `D3DRS_SOFTWAREVERTEXPROCESSING`, `D3DRS_MULTISAMPLEMASK`, `D3DRS_PATCHEDGESTYLE`/`D3DRS_PATCHSEGMENTS`, `D3DRS_DEBUGMONITORTOKEN`, `D3DRS_VERTEXBLEND`/`D3DRS_INDEXEDVERTEXBLENDENABLE`/`D3DRS_TWEENFACTOR` (software vertex blending/tweening — moot since hardware vertex processing is enforced at device creation, but games can still set these defensively), `D3DRS_POSITIONORDER`/`D3DRS_NORMALORDER` (N-patch interpolation order), `D3DRS_WRAP0`..`D3DRS_WRAP7` (stored as one `std::array<DWORD, 8>`, indexed by `index - D3DRS_WRAP0` since the enum values are contiguous).

## Real-game feedback (2026-08-23): silent crash, no diagnostic

Reported: after several builds, the game started crashing with what looks like its own error rather than one of ours -- possibly a memory violation -- with nothing logged from the D3D12 debug layer at all. That combination (native AV, zero D3D12-side diagnostic) is exactly the kind of crash `NOT_IMPLEMENTED()`/`ASSERT`/`FAIL` can't catch, since those only fire on paths we explicitly guarded.

Two things done in response:

1. **`dllmain.cpp` now installs a vectored exception handler** (`AddVectoredExceptionHandler`, registered in `DLL_PROCESS_ATTACH`) that logs to `log.txt` on `EXCEPTION_ACCESS_VIOLATION`, `EXCEPTION_STACK_OVERFLOW`, `EXCEPTION_ILLEGAL_INSTRUCTION`, `EXCEPTION_ARRAY_BOUNDS_EXCEEDED`, `EXCEPTION_INT_DIVIDE_BY_ZERO`, and `STATUS_STACK_BUFFER_OVERRUN` -- the exception code, faulting address, read/write/execute kind (for access violations) and the target address, and the module + offset the crash address falls in (so it's mappable back to source via the PDB even without pulling in `dbghelp` for full symbolication). It always returns `EXCEPTION_CONTINUE_SEARCH` -- this doesn't try to recover or suppress the crash, only to leave a trail in `log.txt` for *next* time this happens, including for crashes not caused by this codebase at all (a genuine game-side bug would also get logged, which is useful for ruling that out). **Next crash: check `log.txt` for a `=== Unhandled exception ===` block before reporting the symptom** — it should narrow down which module/offset actually faulted, even for a "silent" one.
2. **Hardened the most recently-added, least-tested unbounded pointer walk**: `CreateVertexShader`'s new declaration-token copy (added a few commits ago, for `GetVertexShaderDeclaration`) scanned for the `D3DVSD_END()` terminator with no bound -- a malformed/corrupt declaration would walk off into unmapped memory looking for a token that isn't there, which is a plausible match for "silent AV, nothing from D3D12." Capped at 512 tokens (real D3D8 declarations are nowhere near that large) with a clear `FAIL()` if exceeded. `ParseShader`'s existing (pre-existing, not touched by this fix) `D3DSIO_END` scan already has a `default: FAIL()` on any unrecognized opcode, which gives it a comparable safety net without needing the same explicit cap.
3. Added `TRACE_ENTRY` logging to `DrawIndexedPrimitiveUP` (was missing) plus explicit null/zero-stride argument validation, since it's the other recently-added, not-yet-exercised-by-a-real-game code path.

If the vectored exception handler's log entry points at a specific function next time, that's the fastest path to a real fix — far better than guessing from "the game crashed" alone.

## Proactive audit (2026-08-23): DXT/S3TC compressed textures are completely unimplemented -- likely the single biggest remaining compatibility gap

Continuing the enum-completeness audit into texture formats surfaced this: `DXGIFromD3DFormat` (`dx_utils.cpp`) mapped `D3DFMT_DXT1`/`DXT2`/`DXT3`/`DXT4`/`DXT5` straight to `DXGI_FORMAT_UNKNOWN` with no diagnostic. Block-compressed (S3TC/DXT) textures were the standard way games of this era saved VRAM and load-time bandwidth — this is plausibly a bigger real-world compatibility blocker than anything fixed so far this session, and worth flagging clearly even though it isn't fixed here.

**Why it wasn't fixed blind**: the DXT1->BC1/DXT2,3->BC2/DXT4,5->BC3 format mapping itself is unambiguous and trivial. The hard part is everywhere else in `texture.cpp` that computes a pitch or byte size from `Width`/`Height` assumes a flat `width * bytesPerPixel` layout:
- `BaseTexture::BaseTexture`'s `compact_pitches_`/`compact_offsets_`/`total_compact_size_` calculation (the "give games a pitch they expect, not the GPU's padded one" logic) would need to branch on 4x4-texel block dimensions (`ceil(width/4) * bytesPerBlock` instead of `width * bytesPerPixel`, and block-row counts instead of raw pixel rows).
- `GetSurfaceDesc`'s `pDesc->Size = footprint.RowPitch * footprint.Height` multiplies an already block-aware `RowPitch` by the *raw pixel* `Height` — needs the block-row count instead.
- `CopySubresourceToGpuTexture`'s per-row copy loop (`for (uint32_t i = 0; i < footprint.Height; ++i)`) needs verifying against exactly what `ID3D12Device::GetCopyableFootprints` reports for `Height` on a block-compressed subresource before trusting it as a "how many rows to copy" loop bound.

Getting any one of these wrong produces **silently garbled texture contents**, not a crash — a strictly worse failure mode than the current clear one, and not something I can verify correct without a real DXT-compressed asset and a way to see the rendered output. So this is deliberately left as a loud, specific failure rather than a guessed-at partial implementation:

- `DXGIFromD3DFormat` still returns `DXGI_FORMAT_UNKNOWN` for DXT formats (unchanged) — this is load-bearing: `Direct3D8::CheckDeviceFormat` relies on the `UNKNOWN` return to gracefully answer `D3DERR_NOTAVAILABLE` for games that politely *probe* format support before using it, rather than crashing on a mere capability query.
- `BaseTexture::Create` (`texture.cpp`) now explicitly checks for the five DXT formats up front and `FAIL()`s with a specific, unambiguous message identifying the format — this replaces what used to be a confusing generic `FAIL("Unexpected format 0")` several calls downstream (from `DXGIFormatSize` hitting `DXGI_FORMAT_UNKNOWN`'s default case), which didn't hint at DXT being the actual cause at all.

**If a future crash report mentions this specific message, that's the confirmation this is real and worth prioritizing** — implement the three block-math fixes above together (not incrementally, since a still-wrong intermediate state won't obviously look wrong), and ideally verify against a texture with recognizable content so a subtly-wrong block/row calculation shows up visually rather than passing silently.

## Real-game feedback (2026-08-23): `ASSERT` was not reliably fatal -- probable root cause of the "silent crash" reports

Investigating the "crashes with its own error, possibly memory violation, nothing from D3D12" report led to `MessageBoxFmt` (`utils/asserts.cpp`), which backs the `ASSERT`/`ASSERT_HR` macros used **pervasively** across this codebase for invariants (including on D3D12 API call results). Its old behavior:

```cpp
switch (clicked) {
  case IDOK: case IDABORT: exit(1);
  case IDRETRY: __debugbreak(); break;
  default: break;  // <-- IDIGNORE, or the dialog never being seen/clicked at all
}
```

**Only explicitly clicking "Abort" actually terminated the process.** Any other outcome — clicking "Ignore," or the modal dialog never being seen or properly dismissed at all (very plausible for a fullscreen game: the box can render off-screen or behind the game surface, and a stray keypress/click meant for the game can dismiss it via whichever button that input happens to map to) — fell through to `default: break;`, and **execution continued with the violated invariant**. Given `ASSERT_HR` wraps essentially every D3D12 resource-creation call in this codebase, that means a failed `CreateCommittedResource`/`CreateCommandList`/etc. could be silently waved through, leaving a null/garbage `ComPtr` in play -- and the *actual* crash happens later, at some unrelated call site that dereferences that garbage state, with no diagnostic tying it back to the real failure. This matches the reported symptom exactly: a crash that looks unrelated to anything logged, because the real failure already happened and was silently dismissed earlier.

Fixed: every outcome except `IDRETRY` (kept as `__debugbreak()` for interactive use under an attached debugger) now calls `exit(1)`, matching `FAIL`'s `abort()`. There is no invariant in this codebase's actual usage of `ASSERT` where "continue anyway" is safe -- it was never designed as a soft/recoverable warning, this was a latent bug in the dialog-button handling, not an intentional escape hatch.

**This is very likely the actual explanation for the imprecise, hard-to-pin-down crash reports from the last several builds** -- worth treating any *future* crash as a genuinely new symptom now that this is fixed, rather than assuming it's the same recurring issue.

## Proactive audit (2026-08-23): `D3DRS_ZBIAS` tracked but never wired to the PSO

`RenderState::z_bias` is correctly read/written via `Set/GetRenderState` (`D3DRS_ZBIAS`), but `Device::CreatePSO`'s `RasterizerState.DepthBias`/`DepthBiasClamp` are hardcoded to `0`/`0.f` with a bare `// TODO.` (`device.cpp`, not introduced this session). This means Z-bias — the standard D3D8 mechanism for rendering decals/detail overlays coplanar with another surface without z-fighting (bullet holes, blood, ground clutter over terrain, etc.) — is a complete no-op: any game using it will see z-fighting/flickering instead of a clean offset.

**Why this wasn't guessed at**: D3D8's `D3DRS_ZBIAS` is a 0-16 integer scale with no standardized numeric meaning — even on real D3D8 drivers it was implementation-defined how much actual depth offset each unit represented. D3D12's `DepthBias` has a precise, format-dependent formula (`final_depth = original_depth + DepthBias * r`, where `r` is the smallest representable step for the bound depth buffer format), but there's no canonical "correct" conversion from D3D8's fuzzy 0-16 scale to that -- picking a scale factor is a genuine guess, and an overly small one still z-fights while an overly large one visibly floats the decal above the surface. Both look wrong, just differently wrong, and I can't compare against a real screenshot to tune it. Worth implementing with an actual game exhibiting z-fighting decals to tune the scale against, rather than picking a number now and hoping.

## Real-game feedback (2026-08-23): first crash log analysis, Grand Theft Auto: Vice City

First real payoff of the vectored exception handler added earlier today. The game is **Grand Theft Auto: Vice City**, not BF1942/AoM — worth knowing since its DX8 usage patterns may differ. **Acted on the WndProc-reentrancy hypothesis from finding #1 above, since it's a well-documented DXGI gotcha regardless of whether it's the actual root cause of the fatal crash**: `Device::Init` never called `IDXGIFactory2::MakeWindowAssociation` on `window_` after creating the swap chain. Without it, DXGI keeps actively monitoring the game's window itself (intercepting Alt+Enter, reacting to window state changes) -- behavior real D3D8 never had, and exactly the kind of unexpected-to-the-game synchronous window interaction that lines up with the observed reentrancy into `gta-vc.exe`'s own `WndProc` from inside our swap chain setup. Added `MakeWindowAssociation(window_, DXGI_MWA_NO_WINDOW_CHANGES | DXGI_MWA_NO_ALT_ENTER | DXGI_MWA_NO_PRINT_SCREEN)` right after swap chain creation in `Init()` to opt out of all of it. This is standard practice for any DXGI-based wrapper of a legacy API, independent of whether it turns out to be *the* cause of the fatal crash -- worth having regardless.

## `ResizeTarget` was moving the game's own window mid-`Reset`, likely THE fatal-crash cause (fix, unverified pending retest)

Following up on the earlier hypothesis: the actual root cause looks like `Device::Reset`'s unconditional call to `IDXGISwapChain::ResizeTarget`. This codebase never calls `SetFullscreenState` (`presentParams.Windowed` is never even read), so every swap chain here is windowed -- and for a *windowed* swap chain, `ResizeTarget` doesn't just resize the swap chain's buffers, it actually moves/resizes the **target window itself** via `SetWindowPos`. Real D3D8 never touches the app's window like that. `SetWindowPos` synchronously dispatches `WM_WINDOWPOSCHANGING`/`WM_WINDOWPOSCHANGED`/`WM_SIZE` to the window's own `WndProc` -- and the second crash log (with the newly-added call-stack capture) showed exactly this: our code calling into `gta-vc.exe`'s own `WndProc`, which null-derefs (`reading address 0x28`) because the game evidently isn't ready to handle a resize message this early in its own startup sequence, called reentrantly from inside our `Reset()`.

Removed the `ResizeTarget` call entirely; `ResizeBuffers` alone is sufficient to make the swap chain match the window's existing size (we're not the one deciding the window should move). **Not yet confirmed against a real run** -- needs a retest.

## The `ResizeTarget` fix did NOT resolve it -- retest with corrected diagnostics, still open

Retested after removing `ResizeTarget`: **same crash**, still right after `"Resetting device: Submitting commands.."`, `gta-vc.exe+0x23c54e` reading address `0x28`. Ruled out `ResizeTarget` as the cause (or at least as *the whole* cause) -- worth keeping the removal regardless (still correct per the DXGI docs reasoning), but it wasn't sufficient.

Also fixed the crash handler's own bug that produced misleading earlier stack traces: `CaptureStackBackTrace()` called plainly captures the *handler's own* call stack, not the faulted thread's -- switched to walking the EBP chain from `EXCEPTION_POINTERS::ContextRecord->Ebp` (the actual faulted register state), reading through a `__try`/`__except`-guarded helper so a corrupted stack can't cause a second crash inside the handler. This retest's data is trustworthy, and it shows: at the crash, `Ebp` itself is `0x4e3` -- far too small to be a real stack address, meaning either the function at `gta-vc.exe+0x23c54e` doesn't use conventional EBP frame chaining (plausible: `/Oy` frame-pointer omission is common in Release-optimized commercial code from this era) or something register-level is already corrupted by this point. Either way, EBP-walking can't help for *this specific* fault, and there's no PDB for the game's own exe to symbolicate it even if it could.

Since log-reading alone has hit its limit here, added fine-grained `LOG(INFO)` checkpoints around every individual D3D12/DXGI call inside `SubmitAndWait`/`WaitForFrame` (`Close`, `ExecuteCommandLists`, `Present`, `Signal`, `GetCurrentBackBufferIndex`, the fence wait, allocator/list `Reset`) -- deliberately noisy, meant to be removed once this is resolved. The next crash log will show the last-logged checkpoint immediately before the crash, which pins down *which specific call* triggers it, even though the fault itself lands in un-symbolicated game code.

## Checkpoints pinned it inside `Reset()`, past `SubmitAndWait`/`WaitForFrame` themselves -- more logging added

The checkpoints added inside `SubmitAndWait`/`WaitForFrame` paid off: the log showed the full `SubmitAndWait` cycle complete cleanly (`Close` → `ExecuteCommandLists` → `Signal` → `GetCurrentBackBufferIndex` → `WaitForFrame` → allocator/list `Reset`, all logged, `"SubmitAndWait: done"`), then `Reset()`'s own *second*, redundant `WaitForFrame(next_fence_ - 1)` call also completed cleanly (`"WaitForFrame: done"`) -- and *then* the crash, with nothing else logged in between. That means the fault is somewhere in the ~15 lines of `Reset()` after that second `WaitForFrame` call that had no checkpoints yet: `cmd_list_->Close()`, releasing/clearing the old back buffers and depth-stencil texture, `ResizeBuffers`, recreating the depth-stencil texture, re-acquiring the new back buffers via `GetBuffer`, or the final allocator/command-list `Reset`.

Noted in passing: `Reset()` calls `WaitForFrame(next_fence_ - 1)` a second time immediately after `SubmitAndWait(false)` already did the equivalent wait internally. Tracing through `DynamicRingBuffer::HasCompletedFrame`/`SetCurrentFrame`, this redundant second call ends up setting `head_` to the *current* `tail_` position (since by the time it runs, `SetCurrentFrame` has already advanced `current_frame_` and pushed a fresh `{current_frame_, tail_}` entry that this second call immediately consumes) -- not obviously the cause of an immediate crash on the next line, but a real, separate correctness bug in the ring buffer's free-space bookkeeping worth fixing once the fatal crash itself is resolved.

Added checkpoints through the rest of `Reset()`: after releasing old back buffers/depth-stencil, around `ResizeBuffers`, around depth-stencil texture (re)creation, around re-acquiring the new back buffers, and around the final allocator/command-list reset. The next crash log will show exactly which of these is the last one logged before the fault.

## Major breakthrough: the crash is AFTER `Reset()` returns successfully -- likely not our bug at all

The `Reset()` checkpoints from the last commit resolved it: the log showed `"Reset: done"` -- **`Reset()` completed entirely successfully**, all the way through the final allocator/command-list reset. The crash happens *after* that, with nothing else logged, meaning it's in `Device::Init()`'s remaining two lines (`InitRootSignatures(); return S_OK;`), or -- more likely given `InitRootSignatures()` does nothing but internal D3D12 root-signature/cbuffer setup with zero interaction with the game or its window -- **after control returns all the way back to the game**, through `Init()` → `Create()` → `Direct3D8::CreateDevice()` → back into `gta-vc.exe`'s own `CreateDevice` wrapper.

This reframes the whole investigation: every crash signature seen so far (small-offset-from-near-null reads: `0x28`, `0x1`, `0x20`; faulting addresses in unmapped memory or inside `gta-vc.exe`'s own code) is consistent with **the game's own code, immediately after `CreateDevice` returns a valid device, dereferencing something that's null on its side** -- not necessarily anything we're doing wrong. Added `LOG(INFO)` checkpoints at the exact returns of `InitRootSignatures()`, `Init()`, `Create()`, and `Direct3D8::CreateDevice()` (the last line before control returns to the game) to nail down definitively whether the crash is before or after that handoff.

**If the next log shows `"CreateDevice: returning device to caller"` before the crash, this is very likely a bug on the game's side (or a real-vs-our-implementation behavioral difference the game depends on) rather than something in our `Reset`/`Init` sequence** -- would need to shift focus to *what the game does immediately after `CreateDevice` succeeds* (per the earlier static call-site analysis: likely `GetDeviceCaps`, `SetRenderState`, or one of the many `Create*` calls RenderWare makes during its own post-device-creation setup) rather than continuing to suspect `Reset()`/`SubmitAndWait()`, which are now confirmed innocent.

## Confirmed our bug, found via comparison against `d3d8to9` -- missing default vertex format on device creation

User confirmed: the game works fine with the real system `d3d8.dll`, *and* with `d3d8to9` (a well-known, mature D3D8-on-D3D9 compatibility wrapper). That rules out a game-side/OS-compatibility issue definitively -- this is a genuine behavioral gap in this implementation.

Fetched `d3d8to9`'s source (`d3d8to9_base.cpp`, `Direct3D8::CreateDevice`) for comparison. Its last action before returning the newly-created device to the caller: `DeviceInterface->SetFVF(D3DFVF_XYZ);` -- it explicitly primes the device with a default vertex format. This means **a freshly created real D3D8 device already has `D3DFVF_XYZ` (untransformed position-only) active**, not "no format set." Our `Device` never did this: `bound_vertex_shader_` defaults to `0` with *no* corresponding entry in `vertex_shaders_` (populated lazily, only on an actual `SetVertexShader` call) -- a real, observable difference from what every other implementation apparently provides. If a game inspects or relies on a default format being active before it ever calls `SetVertexShader`/`SetFVF` itself (plausible immediately after `CreateDevice` returns, matching exactly where the crash was pinned down to), this exact gap would explain it.

Fixed: `Device::Init` now calls `SetVertexShader(D3DFVF_XYZ)` right before returning, after `InitRootSignatures()` -- this both sets `bound_vertex_shader_` to a valid, real handle *and* creates the corresponding fixed-function `VertexShader` entry in `vertex_shaders_`, matching the state a real D3D8 device is documented/observed to start in.

**Not yet confirmed against a real run** -- needs a retest. If this doesn't resolve it, the `d3d8to9` source is now a proven-useful comparison point for chasing whatever's next -- worth diffing more of its `CreateDevice`/`Reset` path against ours if this specific fix isn't sufficient (e.g. it also does its own present-parameter translation and depth-stencil-format handling that might differ from what we do).

## The `SetVertexShader(D3DFVF_XYZ)` fix had zero effect -- reconsidering whether this crash is even on the same thread

Retested: **byte-for-byte identical crash** (`0x44584749`, `Ebp=0x4e3`, same offsets in the recursive fault) despite the default-vertex-format fix actually changing device state. That a real state change had *zero* observable effect on this crash's signature, combined with the crash reproducing with *exactly* the same address and register values across every single test run regardless of what's been changed in `Device`, is a strong signal this isn't "the game reading uninitialized/wrong device state" at all -- garbage reads from real memory corruption vary between runs (ASLR, allocation timing); a fixed, deterministic repro like this looks more like a *scheduling* coincidence than a causal one.

Compared `d3d8to9`'s `Direct3DDevice8` constructor and `Reset()`/`Present()`/`TestCooperativeLevel()` too (also fetched from source) -- nothing else jumped out as a missing default (it also does no window subclassing or HWND-touching of any kind, for what that's worth re: the earlier `ResizeTarget`/`MakeWindowAssociation` theories).

**New hypothesis**: the crash might be on a **different thread** than the one running `CreateDevice`, with the "right after CreateDevice returns" correlation being coincidental timing (both happen ~140-160ms into the process, independently) rather than causal -- e.g. an asset-loading or watchdog thread the game spins up on its own schedule, crashing on a genuine game-side (or unrelated) issue. Added `GetCurrentThreadId()` to the crash handler's log line, to `CreateDevice`'s "returning device to caller" checkpoint, and as a new breadcrumb on `DLL_THREAD_ATTACH` (so any thread the game creates around this time shows up in the log). **If the next log shows the crash on a different thread ID than `CreateDevice`'s, that redirects this investigation entirely** -- away from `Device`'s creation/reset sequence and toward whatever that other thread is doing.

## Real crash found and fixed: GetRenderTarget/GetDepthStencilSurface broke COM surface identity

The `ddraw.dll` lead turned out not to be needed -- once the deployed DLL was actually rebuilt from the latest source (the previous "znowu crash" logs were stale, from a build predating the thread-ID logging), the new crash log was completely different and much more actionable:

```
=== Unhandled exception 0xc0000005 at 0063C54E on thread 28064 ===
  reading address 0x28
  in F:\Gry\Grand Theft Auto Vice City Dev\gta-vc.exe+0x23c54e
```

Two findings from this:
1. **Same-thread hypothesis confirmed and closed**: crash is on thread 28064, the exact same thread `CreateDevice` returned on. The "different thread" theory from the previous session is dead -- no further need to chase it.
2. **`0x0063C54E` matches, byte for byte, the game's ONLY call site for `IDirect3DSurface8::GetDesc`** per the static call-site analysis (`d3d8_calls_gta-vc.txt`). Reading address `0x28` (not `0x0`) is the signature of a virtual dispatch through an object whose vtable-pointer slot holds a small garbage value (`this` ~= `0x8`, then `this+0x20` for vtable slot 8 = `0x28`) -- i.e. calling through a corrupted/freed C++ object, not a literal null pointer.

Root cause: `Device::GetRenderTarget` and `Device::GetDepthStencilSurface` (`device.cpp`) allocated a **brand-new C++ `GpuSurface`/`BackbufferSurface` wrapper on every single call**, each with its own independent refcount starting at 1. Real D3D8 (and `d3d8to9`, both of which work fine with this game) preserve **COM object identity**: repeated `GetRenderTarget()`/`GetDepthStencilSurface()` calls return the *same* interface pointer (with an incremented refcount) as long as the underlying render target/depth-stencil hasn't changed. Games are entitled to rely on that -- e.g. releasing a previously-fetched surface pointer and expecting a subsequent `GetRenderTarget()` call to still be consistent with any other outstanding reference to "the same" surface. Because our implementation hands out a fresh, independently-tracked object every time, one caller's `Release()` could free an object while the game still held what it believed was another live reference to the identical surface -- a real use-after-free, explaining the garbage vtable pointer.

**Fix** (`device.h`/`device.cpp`): added `cached_render_target_surface_`/`cached_depth_stencil_surface_` (`ComPtr<BaseSurface>`) to `Device`, keyed by the backing texture pointer (`cached_*_surface_key_`). `GetRenderTarget`/`GetDepthStencilSurface` now only construct a new wrapper when the key changes (i.e. the actual bound texture changed, including across a `Reset()` which reallocates back buffers/depth-stencil and so naturally invalidates the cache); otherwise they `AddRef()` and return the existing cached object, matching real COM/D3D8 semantics.

Not yet retested against the game as of this write-up -- next session (or later this session, tokens permitting) should confirm this actually resolves the startup crash, and if any further crash appears, check whether the same "fresh wrapper per call" anti-pattern exists elsewhere (e.g. `GetSurfaceLevel`, `CreateImageSurface`, `GetCubeMapSurface` in `texture.cpp`) -- those weren't audited this pass since the call-site evidence pointed specifically at `GetRenderTarget`/`GetDepthStencilSurface`.

## NEXT SESSION (superseded by the finding above, kept for history): new clue, `ddraw.dll` is also in play

User reports the game (GTA: Vice City Dev) also loads/uses `ddraw.dll` (DirectDraw), alongside `d3d8.dll`. This is a well-known pattern for RenderWare-based games of this era (GTA III/Vice City's RenderWare D3D8 driver historically uses DirectDraw for some combination of: display-mode enumeration before device creation, gamma ramp control, hardware cursor emulation, and/or primary-surface setup) -- it may run in parallel with, or interleaved with, our `Direct3D8`/`Device` calls on the *same* `HWND`.

**Concrete next steps, roughly in priority order**:

If the game sets up DirectDraw exclusive mode on the window either before or after our swap chain claims it, that's a plausible source of exactly this kind of crash. Real `d3d8.dll` obviously coexists with `ddraw.dll` fine in this game -- worth understanding *how* (real D3D8's device creation may leave more of the window's DirectDraw-relevant state alone than DXGI's flip-model swap chain does).

4. If the above doesn't pan out, consider whether **real `d3d8.dll`'s known coexistence behavior with `ddraw.dll`** can be found/documented (their interaction is a well-trodden path for other DX8-era compatibility projects, not unique to this one) -- may be worth a targeted search for how other D3D8 wrappers/community docs describe handling simultaneous ddraw+d3d8 usage in RenderWare-based games specifically.

**Don't restart the crash-chasing from scratch** -- `Reset()`/`SubmitAndWait()`/`Init()`/`InitRootSignatures()` are all now confirmed (via checkpoint logging) to complete successfully every time; the crash is confirmed to happen strictly after `CreateDevice` returns to the caller. That framing still holds regardless of the ddraw angle -- what's now in question is *what specifically* runs in that window, not whether our own device-creation sequence is at fault.

## Phase 6 — Long tail (in progress, reactive)

Second pass (2026-08-23) knocked out the remaining cheap/self-contained ones:

- `MultiplyTransform` — composes the given matrix with the state's current one via `DirectX::SimpleMath::Matrix` (row-vector convention: input matrix applied first, then the existing state), then calls the existing `SetTransform`.
- `GetRasterStatus` — reports a canned "not in vblank, scanline 0" status; this backend has no access to real scanline/vblank timing to report honestly, but a plausible fixed answer beats aborting.
- `SetGammaRamp`/`GetGammaRamp` — plain storage (`gamma_ramp_`, initialized to an identity ramp in the constructor). Deliberately does **not** touch the real display gamma (`SetDeviceGammaRamp`) — that would affect the user's actual monitor output as a side effect of a rendering-compat shim, out of proportion to the value for a feature few games rely on for correctness.
- `DrawIndexedPrimitiveUP` — mirrors `DrawPrimitiveUP` (vertex upload via the dynamic ring buffer) combined with `DrawIndexedPrimitive`'s index-count-from-primitive-type logic, uploading both vertex and index data into the ring buffer per call. Known limitation: unlike `DrawPrimitiveUP`, does not rewrite `D3DPT_TRIANGLEFAN` (rewriting a fan's *index list* is more involved than rewriting a flat vertex list) — `PrepareDrawCall` already rejects fans outright, so this is a pre-existing constraint, not a new gap.

Third pass (2026-08-23) implemented the `Get*ShaderDeclaration`/`Get*ShaderFunction` family:

- `ParseShader` (`shader_parser.cpp`, shared by vertex and pixel shader parsing) now returns a pointer just past the `D3DSIO_END` token instead of `void`, so its callers know exactly how many DWORDs of the input token stream they consumed — reusing the parser's own instruction-length knowledge rather than re-implementing token-stream scanning (which would risk getting some opcode's operand count wrong and mis-copying).
- `VertexShader`/`PixelShader` (`vertex_shader.h`) gained `declaration_tokens`/`function_tokens` vectors, populated in `ParseProgrammableVertexShader`/`ParsePixelShader` from that returned end pointer, and in `Device::CreateVertexShader` for the declaration (scanned separately for its own `D3DVSD_END()` terminator, since the declaration and function are two independent token streams).
- `GetVertexShaderDeclaration`/`GetVertexShaderFunction`/`GetPixelShaderFunction` implement the standard D3D8 "pass `pData = nullptr` to query the required size, then call again with a big-enough buffer" pattern via a shared `CopyOutTokenBuffer` helper.
- Fixed-function shaders (created via the raw-FVF `SetVertexShader(fvf)` path, not `CreateVertexShader`) correctly return `D3DERR_INVALIDCALL` — they have no real declaration/function token stream to return, matching real D3D8 behavior for handles that aren't `CreateVertexShader`-created.

Remaining stubs, 7: `CreateAdditionalSwapChain`, `CreateVolumeTexture`, `DeletePatch`, `DrawRectPatch`/`DrawTriPatch` (RT-patch tessellation — genuinely complex, needs actual tessellation, not attempted blind), `GetFrontBuffer`, `ProcessVertices` (needs either CPU-side vertex shader emulation or a GPU stream-out path — substantial new work). `NOT_IMPLEMENTED()` already logs file/line/function to `log.txt`, so implement these as specific games hit them rather than speculatively.

Texture-side (done, 2026-08-23): `QueryInterface` (matches `IID_IDirect3DTexture8`/`IID_IDirect3DCubeTexture8` by `kind_`, plus the common `IUnknown`/`IDirect3DResource8`/`IDirect3DBaseTexture8` IIDs), `GetDevice`, `SetPriority`/`GetPriority` and `SetLOD`/`GetLOD` (bookkeeping only — no resource-eviction or mip-clamping implementation, we always upload/sample the full chain), `GetType` (derived from `kind_`). `Set/GetPrivateData`/`FreePrivateData` return `D3DERR_NOTAVAILABLE`, matching the same choice already made for surfaces and the palette APIs.

Surface-side, still open: `GetContainer` (would let a mip-level surface answer "what texture do I belong to" via `QueryInterface` on the owning texture — `GpuSurface`/`CpuSurface` already hold that pointer, so this is cheap for those two; left alone only because it's genuinely rare to call and `BackbufferSurface`'s notion of a "container" is ambiguous without a real `IDirect3DSwapChain8` object, which this codebase doesn't expose).

## Real-game feedback (2026-08-23): `Device::Reset` leaking the cached render-target/depth-stencil surface, and a long, ultimately-inconclusive chase of a second `pool_heap.cpp` crash

After the `GetRenderTarget`/`GetDepthStencilSurface` COM-identity fix above was retested, GTA: Vice City hit a **new** crash: `Assertion pool_heap.cpp:30 failed: !free_list_.empty()` — the SRV/RTV/DSV descriptor pool allocator asserting it has nothing left to hand out.

**First, a real bug found and fixed**: `Device::Reset` never cleared `cached_render_target_surface_`/`cached_depth_stencil_surface_` (the caches added by the fix above). Each cached `GpuSurface` holds its own ref on the backing `GpuTexture` (via `ComWrap` in its constructor), so once either accessor had been called at least once, `depth_stencil_tex_->total_ref_count()` stayed at 2 forever — silently defeating the `ASSERT` right after it (dismissable via the message box) and, more importantly, meaning the old `GpuTexture`'s destructor (and the RTV/DSV descriptor it frees) never ran. Fixed by clearing both caches at the top of `Reset()`, before the `total_ref_count()` asserts. Committed (`a3615e3`) — real, worth keeping regardless of the rest of this investigation.

**That fix alone didn't resolve the crash.** What followed was a long live-diagnostic session (temp `LOG` checkpoints added and removed at every layer: `DescriptorPoolHeap::Allocate`, `GpuTexture::InitViews`/`LockRect`/`UnlockRect`, `Device::TransitionTexture`, `Device::SubmitAndWait`, plus thread-ID breadcrumbs and a raw hex-dump-on-corruption helper) trying to catch the exact statement that corrupts `srv_heap_`. Findings, for whoever picks this up if it recurs:

- The heap that actually empties is **`srv_heap_`** (`D3D12_DESCRIPTOR_HEAP_TYPE_CBV_SRV_UAV`), not RTV/DSV/sampler — confirmed by logging `heap_type_` and the `this` pointer at the failing `Allocate()` call and cross-referencing against the addresses logged at `Init()`.
- `CreateDepthStencilSurface`/`CreateRenderTarget`/`CreateCubeTexture` are **not called at all** in this game's traced session — every SRV comes from plain `Device::CreateTexture`, and a full-`TRACE`-level log of one run showed **1875 `CreateTexture` calls, none released** before the crash (this codebase never evicts/frees `D3DPOOL_MANAGED` textures once loaded — each keeps its SRV for its full lifetime) — comfortably past the old `kMaxNumSrvs = 1536`.
- Diagnostic instrumentation added along the way to print `srv_heap_`'s live `num_descriptors_` repeatedly showed it reading as `600` instead of `1536` well before the pool was anywhere near legitimately exhausted, which looked at the time like real memory corruption (single-threaded — confirmed via `GetCurrentThreadId()` on every texture-creation/lock call; not caused by the `DynamicRingBuffer`'s mapped upload-heap pointer overlapping `Device`'s address range — confirmed by logging both). **This was never conclusively explained** — a hex-dump-on-first-corruption helper was added but never actually fired even after the `600` reading reappeared, which in hindsight is the strongest signal that the `600` readings were an artifact of the diagnostic instrumentation itself (most likely a struct-layout/ODR inconsistency from iterating on `pool_heap.h` mid-session — adding accessor methods and a member to a header several times across many rebuild cycles) rather than a genuine pre-existing corruption bug in the shipped code.
- No live memory debugger was available in this environment to settle it definitively: `AddressSanitizer` (`/fsanitize=address`) is wired up behind a commented-out line in `CMakeLists.txt` but is **incompatible with this game** — enabling it made `gta-vc.exe` crash inside its own code before our `DllMain` even finished (likely an allocator/exception-handling conflict, not investigated further); Application Verifier (`appverif.exe`) requires elevation this session didn't have; no x86 `cdb.exe`/WinDbg was installed (only x64 debugger DLLs, no actual debugger binary).

**All temporary diagnostic instrumentation from this chase has been reverted** — none of it was left in the shipped code. The one change that stuck: `kMaxNumSrvs` bumped from `1536` to `8192` (`device_limits.h`) — directly justified by the observed 1875-and-counting legitimate `CreateTexture` call count, independent of whether the `600` corruption reading was real. **Not yet retested against the game as of this write-up.** If the exact same `pool_heap.cpp` assert recurs even with the much larger pool, that's strong evidence the `600` corruption *was* real and independent of pool size — worth re-instrumenting `DescriptorPoolHeap::Allocate()`/`GpuTexture::InitViews()` again at that point (the checkpoints described above are a reasonable starting template), but ideally after either finding an elevated-permissions path to Application Verifier or an x86-capable debugger, rather than repeating the same live-log bisection.

Retested with the larger pool: **the `pool_heap.cpp` assert did not recur.** The game went on to hit several more, unrelated real gaps this same session (all fixed): an overly strict `written_ranges_.ranges.size() == 1` assert in `DynamicBuffer::PersistDynamicChanges` (real usage produces multiple non-contiguous ranges; `buffer.cpp`), missing `D3DTSS_COLORARG0`/`ALPHAARG0`/`RESULTARG` bookkeeping plus actual `D3DTOP_MULTIPLYADD`/`LERP` pixel-shader codegen (`render_state.h/.cpp`, `ff_pixel_shader.cpp`), missing `D3DPT_LINESTRIP` in `CreatePSO`'s primitive-type switch (`device.cpp`), and — the biggest one — pretransformed (`D3DFVF_XYZRHW`) vertices getting a spurious hardware perspective-divide because the vertex shader copied the app's raw RHW value straight into `oPos.w` instead of forcing it to `1` (`ff_vertex_shader.hlsl`); visible as the game's pause-menu background rendering as a skewed trapezoid instead of a flat rectangle. Also disabled `SetEnableGPUBasedValidation(TRUE)` (`device.cpp`) — it reports errors asynchronously relative to the CPU call that triggered them (confirmed: a validation error logged ~350ms after the last real `ExecuteCommandLists`, checkpoint log dead silent in between), which is actively misleading when checkpoint-chasing a crash, and it was very likely the cause of an earlier report of ~20 FPS even in menus.

With all of the above in, the game reached actual playable gameplay — correct HUD, correctly-flat UI, character/vehicles/world rendering normally, ~30-40 FPS.

## Real-game feedback (2026-08-23): "PSO deleted while still referenced by the command list" is a third-party overlay, not our bug

One more crash surfaced during actual gameplay (not loading): `ID3D12CommandList::Close: An ID3D12PipelineState object ... referenced in the command list being closed ... was deleted prior to closing the command list.` Recurred twice, both times with an on-screen FPS/CPU/GPU/latency overlay visible in the user's screenshot (a RTSS/MSI Afterburner-style OSD, injected into the process) and correlated with the user taking a screenshot via the Windows Snipping Tool at the moment of the crash.

Added temporary thread-ID cross-checks (`GetCurrentThreadId()` logged in `SubmitAndWait`, `PrepareDrawCall`, and `DebugInfoQueueMessageCallback`, comparing against the previous call's thread) to test whether a second thread was touching `cmd_list_`/`pso_cache_` concurrently — the kind of race that would explain a PSO's refcount hitting zero while still bound to an open command list. **Confirmed by direct A/B test instead**: user reproduced the crash with the overlay active, then played the same way with the overlay/screenshot tool closed and it did not recur. `pso_cache_` itself was independently checked and never erases entries once inserted (see the earlier `srv_heap_` investigation above for the full list of PSO-lifetime call sites checked) — there is no code path in this project that would release a cached PSO out from under an in-flight command list on its own.

Conclusion: this is a known class of incompatibility between hand-rolled/minimal D3D12 usage (like this shim) and third-party overlays that hook `Present`/`ExecuteCommandLists` to inject their OSD or capture a frame — those hooks are mostly tested against mainstream engines' D3D11/D3D12 usage patterns, not against a bespoke D3D8-on-D3D12 shim, and can end up replaying or reordering command-list submission in a way that races the app's own resource lifetimes. **Not a bug to fix in this codebase** — the actionable guidance is simply to play without an FPS/performance overlay active, and to avoid taking screenshots via tools that hook the graphics pipeline while testing. Reverted all temporary thread-ID diagnostic logging (none shipped).

The user then made a fair pushback: the game genuinely shouldn't hard-crash just because a third-party overlay is active, even if that overlay isn't this codebase's bug. Agreed and fixed: `DebugInfoQueueMessageCallback` now only aborts on `D3D12_MESSAGE_SEVERITY_CORRUPTION` (real GPU/driver memory corruption), not `ERROR` — ERROR-severity validation messages still log to `log.txt` (so real bugs remain diagnosable) but no longer kill the process. This trades "abort loudly the instant the debug layer complains" (right for developing this codebase) for "keep the game running through a validation-layer false positive triggered by something outside this codebase's control" (right for someone actually trying to play).

## Proactive audit pass (2026-08-23): static-analysis-style sweep for the same "ASSERT-what-should-be-a-real-code-path" pattern

With the game reaching actual playable gameplay, did a manual audit of every `ASSERT`/`FAIL` in `device.cpp`/`texture.cpp`/`surface.cpp`/`direct3d8.cpp` looking for the same shape of bug `CopyRects` and partial-rect `Lock` turned out to be: an invariant that's true for the *simplest* case but not the general one a real game can easily hit. Found and fixed, without a live game session to verify against (deployed but not retested as of this write-up):

- **Partial-rect `LockRect` was universally unsupported** — `CpuTexture`, `GpuTexture`'s `D3DPOOL_MANAGED` delegation, `GpuSurface`, `CpuSurface`, and `BackbufferSurface` all `ASSERT`'d `pRect == nullptr`. Partial-rect locking (streaming/updating part of a texture without touching the rest) is a common, unremarkable technique — this would have crashed the instant a game used it. Fixed by offsetting the returned `pBits` by `top * pitch + left * bytes-per-pixel` and keeping the full row pitch, the same convention as a whole-surface lock where the caller only touches the region it cares about. `LockGpuReadback` (shared by the two GPU-readback-backed cases) gained a `pRect` parameter for the same treatment.
- **`Clear` only supported a single rect** (`ASSERT(Count == 1)`) despite `D3DRECT*`/`Count` being a real array in the D3D8 API. Generalized to loop over the actual array. Along the way, found `ClearRenderTargetView`/`ClearDepthStencilView` were called with `NumRects` hardcoded to `0` regardless of whether rects were supplied -- meaning even the one rect that *was* supported was silently ignored and the entire target got cleared every time. Fixed to pass the real count.
- **`D3DLIGHT_SPOT` was actively rejected**: `Device::PrepareDrawCall`'s light-marshalling `ASSERT`'d no enabled light was a spotlight, and even bypassing that, `lighting.hlsl` unconditionally zeroed spotlight contribution. Implemented the real D3D8 cone-falloff formula (the `theta`/`phi`/`falloff` fields were already being marshalled into the lights cbuffer, just never read).
- **`CheckDeviceFormat` crashed on any `D3DRTYPE_TEXTURE`/`CUBETEXTURE` capability query with a non-`RENDERTARGET` usage flag** (`ASSERT(Usage == 0)` after only masking off `D3DUSAGE_RENDERTARGET`) — `D3DUSAGE_DYNAMIC` being the obvious one a game would query before ever calling `CreateTexture`. Since dynamic textures genuinely aren't implemented (`CreateTexture` `FAIL`s on them), now reports them as unsupported via the capability query too, so a well-behaved game gets a graceful "no" instead of a crash before it ever reaches actual texture creation.
- **`D3DTSS_BUMPENVMAT00/01/10/11`/`BUMPENVLSCALE`/`BUMPENVLOFFSET` had no storage at all** in `TextureStageState`, so `SetTextureStageState` would `FAIL` in `GetAtIndex` the instant a game set them. Added bookkeeping fields (matching the `COLORARG0`/`ALPHAARG0`/`RESULTARG` treatment from earlier this session) since the game has already been observed requesting `D3DFMT_V8U8` textures — the standard signed bump-map format, a reasonable signal `D3DTOP_BUMPENVMAP`/`BUMPENVMAPLUMINANCE` could be next. **Note this is bookkeeping only** — actually rendering the bump effect requires perturbing the *next* texture stage's sample coordinates using the current stage's result, which doesn't fit `ApplyOperation`'s per-stage-independent formula in `ff_pixel_shader.cpp` and would need real shader-generation restructuring. Not attempted blind; `ApplyOperation`'s `default: FAIL` still fires if a stage's color/alpha op is actually set to one of these two ops. If that's ever hit, this is the next real gap to close.

Also audited (and left alone, on purpose): the programmable vertex/pixel shader parser's `ASSERT`s (`shader_parser.cpp`, `vertex_shader.cpp`) are bounds/format checks on the DX8 bytecode token stream, not "only the simple case is supported" shortcuts — no evidence of a specific failing shader to diagnose against, and guessing at bytecode-parsing edge cases without a concrete failing case risks introducing a real bug for a hypothetical one. `Buffer::Lock`'s `ASSERT(!HasFlag(Flags, D3DLOCK_DISCARD))` (static, non-dynamic buffers) is lower-confidence than the fixes above — real D3D8 drivers treat `DISCARD` on a static buffer as a no-op rather than an error, so `ASSERT`ing it never happens is arguably too strict, but no concrete evidence this game actually does it; worth revisiting if a static-buffer-related crash shows up.
